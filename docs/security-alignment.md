# Best Practices and Security Alignment Update

## On-device voice recognition and permission boundary

- **Improvement description:** Voice-guided menu discovery is implemented as a
  guest-initiated, on-device transcription input. Microphone permission is
  requested only after the guest taps **Speak**. The transcript enters the same
  editable query path as keyboard text and cannot confirm an intent, shortlist
  a dish, create a handoff, or order anything by itself.
- **Priority level:** High
- **Impact:** Limits microphone use, prevents silent cloud-recognition fallback,
  avoids stale speech callbacks changing a later session, and preserves the
  existing allergy-intent confirmation boundary.
- **Alignment action:** Android 12+ uses
  `createOnDeviceSpeechRecognizer()` only after
  `isOnDeviceRecognitionAvailable()`. Older or unsupported devices fail to an
  explicit keyboard fallback. Recognition cancels on lifecycle stop and is
  destroyed when the intake route leaves composition. Transcript candidates
  are normalized and bounded to 500 characters; audio and transcripts are not
  logged.

### Android Intent security assessment

The recognition `Intent` is created inside the app and passed directly to the
on-device `SpeechRecognizer`; no incoming or nested Intent is forwarded. Voice
adds no Activity, service, receiver, provider, `PendingIntent`, or exported
component. The optional **Open settings** fallback constructs only
`Settings.ACTION_APPLICATION_DETAILS_SETTINGS` for MenuPilot's own package URI,
adds no extras or URI grant flags, and handles missing/blocked handlers with the
keyboard still available.

## Policy-gated pairing recommendations

- **Improvement description:** Catalog highlights and shortlist pairings are now
  generated by a deterministic exact-variant engine that calls the existing
  menu policy engine for every recommendation computation.
- **Priority level:** High
- **Impact:** Prevents popularity, restaurant merchandising, or historical
  co-order data from making an allergen-conflicting, unavailable, stale-fact, or
  unknown-fact dish orderable.
- **Alignment action:** Suggestions carry item ID, variant ID, and recipe
  revision; require an approved restaurant pairing or current aggregate
  affinity for shortlist placement; exclude shortlisted and dismissed variants;
  and are capped at two. The app also tracks accepted pairing identities so
  sequential refreshes cannot exceed the two-pairing product cap. Adding a
  pairing routes through the same guarded shortlist path and invalidates any
  prior waiter acknowledgment. Dismiss does not mutate the shortlist.

## Safe external review handoff

- **Improvement description:** The Google action accepts only an
  application-owned restaurant configuration URL, validates it against a
  narrow HTTPS host allowlist, and launches it only after an explicit guest
  tap. The guest-edited public draft is copied separately only after that tap;
  it is never attached to the Intent or posted automatically. The private note
  is never copied to Google.
- **Priority level:** Medium
- **Impact:** Reduces malicious destination, credential-in-URL, unexpected
  scheme, nonstandard-port, and URI-permission risks at the inter-app boundary.
- **Alignment action:** Uses a plain `ACTION_VIEW` + `CATEGORY_BROWSABLE`
  implicit Intent for the intended system-wide browser/Maps handoff. The
  Intent has no nested Intent, extras, component forwarding, grant flags, or
  mutable `PendingIntent`. Launch failure is handled without exposing internal
  details.
- **Guest-control action:** Generated text is editable and starts unapproved.
  The Google Maps action is disabled until the guest explicitly chooses to use
  the current text as their public draft; editing it clears approval.

## Concierge waiter-handoff boundary

- **Improvement description:** The previous order-completion path was replaced
  with a guest-controlled shortlist and a local waiter-handoff reference.
- **Priority level:** High
- **Impact:** Prevents the tablet from implying that a dish is ordered,
  accepted by the restaurant, available from the kitchen, or approved for an
  unresolved allergy/preparation question.
- **Alignment action:** `createWaiterHandoff()` re-runs the deterministic menu
  policy and verifies the confirmed intent fingerprint, menu revision, policy
  version, item ID, variant ID, and recipe revision for every shortlisted dish.
  It creates only an `MP-H-####` local reference. Any unresolved question stays
  visible in the handoff for a human waiter and kitchen to confirm. The
  prototype performs no network call and has no POS, kitchen, payment, or
  order-submission adapter.

## Neutral feedback and review-routing boundary

- **Improvement description:** The post-meal flow now gathers five practical
  dimensions, optional tags, a restaurant-only note, and an optional manager
  follow-up request before generating an editable public draft.
- **Priority level:** High
- **Impact:** Gives the restaurant actionable private feedback without review
  gating, preserves guest control of public speech, and prevents private
  content from crossing into the Google handoff.
- **Alignment action:** Private restaurant feedback and the Google destination
  are both returned by `availableDestinations` for every rating. The private
  payload is typed separately and includes the private note. The Google path
  copies only `generatedReview`, opens an allowlisted external page on explicit
  tap, and never pre-fills a Google rating or posts content. No reward or
  incentive is offered.
